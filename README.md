# cartcell-mhc2-predictor

MHC-II peptide binding affinity/classification predictor, rebuilt locally on top of
the [`s7776d/CapsNet-MHC`](https://github.com/s7776d/CapsNet-MHC) base framework
after the original project's server (`eantec-server`) became unreachable and its
custom code was lost.

This repo contains **only the code and data we rebuilt** (`codes/custom_codes/` +
generated `custom_dataset/`) -- not the upstream base framework (its `Anthem_codes`,
`IEDB_codes`, sample `dataset/`), which you get by cloning the base repo above.
`codes/custom_codes/` is designed to sit inside a clone of that base repo at
`CapsNet-MHC-main/codes/custom_codes/` (its relative import/data paths assume that
layout), so to actually run it: clone the base repo, drop this repo's
`codes/custom_codes/` and `custom_dataset/` into it at the same paths (overwriting
nothing else), then follow the Quickstart below.

### 5-fold CV results (OOF)

| Model | AUROC | AUPRC | Pearson r | MSE |
|---|---|---|---|---|
| Phase2 | 0.860 | 0.319 | 0.408 | 0.060 |
| Phase3 | 0.826 | 0.257 | 0.517 | 0.052 |
| Ensemble (alpha=0.5) | 0.862 | 0.328 | 0.507 | 0.053 |

Phase3 trades a little classification AUROC for meaningfully better regression
(Pearson r, MSE) than Phase2 -- the pattern the original project's briefing
describes. Ensemble sits at a good balance point; the alpha sweep in
`reports_ensemble/alpha_sweep_oof.csv` shows AUROC peaks near alpha=0.65 and
Pearson r peaks near alpha=0.2.

## Known limitation: placeholder pseudo-sequences

The 34-residue MHC-II allele "pseudo-sequence" encoding (`mhc_pseudo.py`) is
currently a **deterministic placeholder** (SHA256 hash of the allele name mapped to
amino acid letters) rather than a real IMGT/HLA-derived sequence. This was already
an unresolved TODO in the original project before the server was lost (see
`docs/cartcell_rebuild_briefing.md` section 1.4), not something introduced here.

Consequence: the model can't learn real cross-allele binding-groove similarity --
two biologically near-identical alleles (e.g. `DRB1*15:01` / `DRB1*15:02`) get
completely unrelated placeholder vectors, since cryptographic hashing is designed
to make similar inputs produce dissimilar outputs. This caps regression
performance and specifically undermines LOMO (which tests generalization to
alleles unseen in training -- exactly the case placeholder vectors can't support).
All models here use the *same* placeholder scheme, so relative comparisons
(Phase2 vs Phase3 vs Ensemble) stay valid; only the absolute performance ceiling
is affected. Fixing this needs real IMGT/HLA protein sequences plus a
NetMHCIIpan-style binding-groove contact-residue position list -- tracked as a
follow-up, not done in this snapshot.

## Structure

```
codes/custom_codes/
  seq_encoding.py       BLOSUM62 peptide encoding (23-dim) + reduced allele encoding (10-dim)
  mhc_pseudo.py          allele name normalization + pseudo-sequence lookup (placeholder, see above)
  data_pipeline.py        raw CSV -> IC50 transform -> affinity/label -> train/test split
  data_provider.py       TSV -> encoded batches
  models/
    common.py             CoreRegister, PseudoSeqEncoder, DynamicRouting (squash + routing-by-agreement)
    phase2.py             Phase2Model: CNN + Core Register
    phase3.py             Phase3Model: 3-branch CapsNet (56 primary capsules) + Dynamic Routing
  losses.py               Phase2Loss / Phase3Loss (multi-task: BCE + MSE + entropy penalty)
  train_phase2.py         5-fold CV training, resumable per fold
  train_phase3.py         5-fold CV training, resumable per fold, warm-starts from Phase2
  ensemble.py             alpha-sweep + default alpha=0.5 mix of Phase2/Phase3 predictions
  lomo.py                 leave-one-allele-out evaluation, resumable per (allele, model)
  evaluate.py             AUROC/AUPRC/Pearson r/MSE, pooled + per-allele
  resume_utils.py         shared per-fold resume/checkpoint helpers
  config/                 data.json, phase2.json, phase3.json, lomo.json
  run_*.sh                thin wrappers around the *.py entry points
custom_dataset/Anthem_dataset/
  raw/merged_data_without.csv   source data (34,411 peptide-allele pairs)
  train_data.txt, test_data.txt  generated by data_pipeline.py
  mhc_ii_pseudo.csv               allele -> pseudo-sequence table (placeholder)
docs/
  cartcell_rebuild_briefing.md    original project spec, reconstructed from chat history
  cartcell_server_state.md        lost server's data/results/bugfix notes, reconstructed from chat history
```

## Quickstart

```bash
cd codes/custom_codes

# 1) regenerate the dataset
bash run_pipeline.sh

# 2) smoke tests
python models/phase2.py --selftest
python models/phase3.py --selftest
EPOCHS=2 N_FOLDS=2 bash run_train_phase2.sh
EPOCHS=2 N_FOLDS=2 bash run_train_phase3.sh

# 3) full training (CPU; hours)
bash run_full_training.sh      # Phase2 5-fold x30ep -> Phase3 5-fold x40ep, resumable
python ensemble.py
python lomo.py                 # ~50h; ALLELE_LIMIT=5 for a quick subset instead
```

All three training entry points (`train_phase2.py`, `train_phase3.py`, `lomo.py`)
write their result for each fold/allele to disk immediately and skip anything
already on disk on the next run -- a run interrupted by e.g. the machine sleeping
resumes instead of starting over.

See `codes/custom_codes/README.md` for full details on each script, and
`docs/` for the original project spec and server-state reconstruction this
rebuild is based on.
